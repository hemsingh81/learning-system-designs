## Narrative

**As** Preeti Singh, operations analyst at Northwind
**I want** one screen showing every document the system could not read confidently, with the failing fields marked and the PDF beside them
**So that** I can fix forty documents in a morning without opening a file share, a spreadsheet, and an email chain for each one.

## Acceptance criteria summary

1. One queue, listing every document rejected by the rules engine, oldest first, filterable by counterparty and by reason.
2. Selecting a row opens a two-panel view: the rendered PDF on the left, the field list on the right.
3. **The PDF opens at the page the failure was found on**, not at page one.
4. Selecting a failing field scrolls and highlights the corresponding region on the PDF. Selecting a region on the PDF selects the field. The two panels stay in sync.
5. **Every failing field is shown at once**, not the first. Fixing one and resubmitting to find the next is unacceptable.
6. Each field shows: the value the model read (editable), the confidence **as a percentage**, the threshold it needed to meet, and the reason in ordinary words.
7. The analyst can correct a value, release the document, or reject it with a reason.
8. Releasing a document re-runs the rules engine against the corrected values. A correction that still fails returns to the queue with the new failures.
9. Corrections are attributed to the analyst and timestamped. The original extracted value is retained.
10. Account numbers are masked in the list view — last four digits only. Full value visible in the detail panel.
11. Keyboard-first. An analyst can work a document end to end without the mouse.
12. Every component has a defined loading, empty, error, and success state. An empty queue is a designed screen, not a blank page — it is the state Preeti will see most often once the straight-through rate reaches target.
