## Narrative

**As** the ingestion pipeline
**I want** to know which counterparty layout a document is before I try to read it
**So that** the right extraction model is used, and a document I do not recognise reaches a human rather than being read with the wrong model and producing plausible nonsense.

## Why it matters

Using the wrong extraction model does not fail loudly. It returns fields — the wrong ones, with respectable confidence scores, because the model is confident about the thing it thinks it found. A misclassified document is therefore more dangerous than an unclassified one.

## Acceptance criteria summary

1. Each document is classified with the custom classifier `counterparty-doc-classifier-v2`.
2. The classifier returns a document type and a confidence score.
3. **Below 0.75 classifier confidence, the layout is never guessed.** The document goes to the exception queue with reason `unrecognised_layout`.
4. A classification result routes the document to exactly one `SourceConfig` in `config/sources.yaml`.
5. Blob path prefix (`broker_alpha/`, `broker_beta/`) is the routing fallback where the counterparty delivers on a dedicated SFTP path.
6. Classification result, confidence, and the resolved source key are logged on every document.
7. Adding a counterparty to the classifier is a YAML entry plus a trained model. No Python change.
8. Classifier cost is charged at roughly $3 per 1,000 pages and must be visible separately in cost analysis from extraction.

## Notes

- 0.75 is the same number as the string-field extraction threshold, and that is a coincidence, not a shared constant. They are configured separately (`classifier.min_confidence` vs `confidence.by_field_type.string`) because they will diverge the first time a counterparty adds a layout that looks like another one.
- The classifier is billed per page like extraction, but it only needs the first page. Ravi capped submission to page 1 for classification, which is where most of the modelled $38/month comes from rather than $114.
